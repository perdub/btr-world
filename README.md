# BTR World — мир «Одинокого рокера» — 0.1.0

Серверный прототип для **Minecraft Java 1.21.1**, Fabric и Polymer. Сделан для Алиски. Округлые тсум из предоставленного референса адаптированы в ступенчатые Minecraft-модели; это собственные простые кубические модели, а не импорт готовых фигурок.

## Что включено

- 8 приручаемых спутников: Хитори, Нидзика, Рё и Кита, каждая в формах тсум и чиби.
- Следование, ожидание, сохранение хозяина и состояния при перезапуске.
- Хитори прячется в визуальную коробку, когда в радиусе 5 блоков есть враждебный моб.
- Рё ест траву и лечится. При `mobGriefing=false` трава не разрушается. Прирученная Рё обменивает один изумруд на случайную фигурку, только для своего хозяина.
- Кита сияет частицами и контуром. Хозяин в радиусе 8 блоков получает ночное зрение. Это не динамический источник света.
- Нидзика каждые 10 секунд даёт хозяину рядом 5 секунд спешки и играет тихий барабанный удар.
- 36 строительных блоков: четыре палитры × три оттенка × матовый блок/кафель/светильник.
- 4 фигурки на подставках и 7 предметов декора: коробка, усилитель, колонка, барабаны, микрофон, кейс и вывеска STARRY.
- Коробка при нажатии даёт игроку 10 секунд невидимости, перезарядка 20 секунд. Это упрощённая механика укрытия; посадка игрока внутрь и накопление вдохновения пока не сделаны.
- Барабаны при нажатии дают 10 секунд спешки. Гитара по ПКМ отталкивает враждебных мобов в радиусе 4 блоков, перезарядка 5 секунд.
- 56 рецептов для выживания, выпадение всех блоков при разрушении, русский и английский языки.
- Редкое появление спутников в равнинах, лесах и лугах. Новые встречи зависят от обычного лимита мирных мобов.
- `/bocchi stage` создаёт небольшую сцену перед игроком по направлению мировой оси +Z. Нужны права оператора 2 и свободный объём 7×4×5. Существующие блоки не заменяются.

## Установка

1. Создайте профиль или сервер **Fabric для Minecraft 1.21.1**. Для запуска нужна **Java 21**.
2. Установите **Fabric API 0.102.1+1.21.1**, **Polymer bundled 0.9.18+1.21.1** и `btr-world-0.1.0.jar` в папку `mods` сервера. Для одиночной игры эти же моды ставятся в профиль игры.
3. Нужен ресурспак Polymer: без него собственные модели и текстуры не будут отображаться.
4. На выделенном сервере используйте AutoHost, включённый в bundled Polymer. После первого запуска откройте `config/polymer/auto-host.json`, измените `"enabled": false` на `"enabled": true` и перезапустите сервер. Полная документация: https://polymer.pb4.eu/latest/user/resource-pack-hosting/ . При подключении примите ресурспак сервера. Если AutoHost не используется, сгенерируйте пакет командой `/polymer generate` и настройте раздачу через `server.properties`.
5. Обычному клиенту на выделенном сервере не требуется этот мод, однако требуется принятый серверный ресурспак. В одиночной игре Polymer может подключить ресурсы локально.

Загрузки зависимостей: https://modrinth.com/mod/fabric-api/versions?g=1.21.1 и https://modrinth.com/mod/polymer/versions?g=1.21.1 . Зависимости не вложены в архив мода.

## Творческая вкладка и приручение

В творческом режиме выполните `/polymer creative`, затем выберите отдельную вкладку **BTR World**. В ней собраны все 56 игровых предметов: 8 предметов призыва спутниц, 36 цветных строительных блоков, 4 фигурки, 7 украшений и гитара. Технические предметы моделей отображения скрыты из списка. Предмет «Позвать» используется ПКМ по поверхности и создаёт дикую спутницу. Вкладка Polymer синхронизируется с сервером; клиентам на выделенном сервере устанавливать мод не требуется.

| Спутница | Угощение для приручения и лечения |
|---|---|
| Хитори | Печенье |
| Нидзика | Торт, используемый как предмет, а не поставленный блок |
| Рё | Пшеница |
| Кита | Светящиеся ягоды |

Одно угощение гарантированно приручает. После приручения ПКМ **пустой рукой по нижней части модели** переключает «следовать / ждать». Другие игроки не могут переключать режим. Бирки и поводки поддерживаются. Владелец сохраняется через UUID. При большом расстоянии используются обычные правила телепортации прирученных спутников; сидящие остаются на месте. Спутники не размножаются.

Пример команды оператора: `/give @s bocchi:bocchi_plush_summoner` или `/give @s bocchi:ryo_chibi_summoner`.

Рецепт призыва: белая шерсть (тсум) или дубовые доски (чиби) сверху по центру, печенье в центре, два красителя по бокам, осколок аметиста снизу. Цвета: розовый/жёлтый/синий/красный. Рецепты автоматически открываются при первом тике игрока.

## Ограничения прототипа

Модели статические: спутницы движутся и поворачиваются, но ноги, волосы и руки отдельно не анимируются. Модель рисуется стандартной display-сущностью, связанной с невидимым мобом; у неё отдельная визуальная часть и небольшая область взаимодействия. Декор можно проходить насквозь, цветные строительные блоки имеют обычную кубическую коллизию. Декор пока не поворачивается при установке.

Пока отсутствуют: розовый гаст, героини со скинами игроков, естественная генерация репетиционных комнат и киосков, полноценная концертная ритм-игра. Команда сцены создаёт готовую композицию из блоков.

Гарантия работоспособности в игровом мире зависит от проверки в Minecraft. Смотрите `VALIDATION.md`: там указаны выполненные проверки и то, что ещё не проверено.

## Сборка исходников

Java 21, Gradle 8.8. После распаковки: `gradlew.bat build` на Windows или `./gradlew build` на Linux/macOS. Если wrapper отсутствует, используйте `gradle build` с установленным Gradle 8.8.

Исходники Java лежат в `src/main/java/dev/aliska/bocchi`. Ресурсы — в `src/main/resources`. `scripts/generate_assets.py` воспроизводит модели, текстуры и рецепты (Python 3 + Pillow). `scripts/validate_assets.py` проверяет ссылки и геометрию. `scripts/render_preview.py` строит превью из реальной геометрии JSON; превью не является скриншотом игры.

## GitHub CI/CD и постоянная ссылка

Workflow `.github/workflows/build-release.yml` проверяет ресурсы и собирает мод на каждом push и pull request. Успешный push в **основную ветку репозитория** автоматически создаёт отдельный GitHub Release и делает его latest. Также доступен ручной запуск через Actions → Build and publish mod → Run workflow на основной ветке. Push в другие ветки и pull request только проверяются, без публикации.

Внутренняя версия сборки: `0.1.0+build.<номер запуска>.<короткий SHA>`. Базовую версию меняйте в `gradle.properties`, поле `mod_version`. Каждый релиз хранит отдельный тег `build-<run_id>-<short_sha>`; предыдущие релизы остаются доступны. Старый коммит при повторном запуске не заменяет latest. Все файлы сначала загружаются в draft, и только затем релиз публикуется.

**Постоянный адрес JAR** (замените OWNER и REPO на свои):

```
https://github.com/OWNER/REPO/releases/latest/download/btr-world.jar
```

Исходники: тот же адрес с именем `btr-world-sources.jar`. Контрольные суммы: `SHA256SUMS.txt`. Это стабильные адреса, которые перенаправляют на файлы последнего опубликованного релиза; содержимое обновляется после новых успешных сборок. Для конкретной неизменной сборки используйте ссылку её тега, а не latest.

### Первый запуск

1. Распакуйте исходники и загрузите **содержимое папки проекта** в корень GitHub-репозитория: рядом должны лежать `build.gradle`, `gradlew`, `src` и `.github`. Не помещайте их внутрь дополнительной папки репозитория. Включите скрытые файлы при загрузке `.github`.
2. Включите Actions, если GitHub предлагает это при первом запуске. Workflow использует встроенный `GITHUB_TOKEN` с `contents: write` только для публикации; отдельный PAT не нужен. Политика организации должна разрешать эту запись и создание тегов/релизов.
3. Сделайте push в основную ветку (`main`, `master` или другое имя) и дождитесь успешных jobs `build` и `publish`.
4. После первого опубликованного релиза постоянная ссылка начнёт работать. У публичного репозитория скачивание доступно без авторизации; у приватного — только с доступом и авторизацией.

В архиве workflow подготовлен, но запуск на GitHub ещё не выполнен: репозиторий пользователя не указан. В CI не запускается игровой мир и не принимается EULA. Локальные обходы ограничений среды сборки из VALIDATION.md не нужны стандартному GitHub runner.
